# Lattice PCS evaluation

This experiment compares Akita (direct and setup-offload), Greyhound, and
RoKoKo on **dense** polynomial openings. It is the source of `tab:eval-lattice-time` and
`tab:eval-lattice-resources`. Generated reports also record the host CPU,
whether AVX-512F was advertised, and the recorded implementation revision per
row. Treat it as a native-workload survey unless security and statement
assumptions match.

Akita is measured twice: the direct generated `fp32-dense` schedule, and the
same pin with **recursive setup offloading** (`akita-offload` /
`fp32-dense-recursive`). Offload rows use `RecursiveCommitmentConfig<fp32::Dense>`.
The recursive catalog is generated with that revision's planner
(`scripts/extend-akita-fp32-dense-offload.sh`) and installed from
`vendor/akita-catalogs/`. At \(n_v=22\) (payload \(2^{27}\)) that planner
emits a row with no setup-prefix edge; the offload cell is recorded as an
error rather than a silent fallback to the direct catalog.

## What is being compared

Nominal payload is the target value of \(N \log_2 |\mathbb{F}|\). Akita and Greyhound
use \(q = 2^{32}-99\), so payload \(2^{k}\) means \(\log_2 N = k-5\). RoKoKo
uses \(q = 2^{50}-2687\) and ships native sets `p-22`, `p-24`, `p-26`, `p-28`,
and `p-30`. These have the same coefficient counts as the corresponding Akita
and Greyhound rows, but they are not bit-identical payloads.
RoKoKo samples bounded 31-bit coefficients despite its ~50-bit native field,
so the nominal \(25/16\) field-capacity ratio is not sampled information
content and must not be used to rescale throughput.

| Payload | Akita / Greyhound \(\log_2 N\) | RoKoKo |
| ---: | ---: | --- |
| \(2^{27}\) | 22 | `p-22` (\(\log_2 N = 22\)) |
| \(2^{29}\) | 24 | `p-24` (\(\log_2 N = 24\)) |
| \(2^{31}\) | 26 | `p-26` (\(\log_2 N = 26\)) |
| \(2^{33}\) | 28 | `p-28` (\(\log_2 N = 28\)) |
| \(2^{35}\) | 30 | `p-30` (\(\log_2 N = 30\)) |

The comparison is **single-threaded**. RoKoKo has no native multithreaded
prover. Greyhound's reference can parallelize extension products; this harness
sets `LATTICE_DOGS_THREADS=1` so the ratio is not a parallel-scaling artifact.
Every worker is launched as a fresh process. Peak RSS is that process's
`VmHWM` and includes the dense witness. The
virtual-address-space ceiling is numerically **90% of host RAM**
(`scripts/with-memlimit.sh` / `ulimit -v`), so a 121~GiB machine grants about
109~GiB of address space to each worker. Only corroborated allocation failures
are `oom`; an unexplained SIGKILL remains an error.
Greyhound uses the `l2-quantum128-adps16` Euclidean SIS policy (128-bit
quantum ADPS16 core-SVP). Proof sizes are the contextual wire encoding:
public `u1` and the fold schedule are verifier context. If Greyhound still
cannot secure the Ajtai commitments, the cell is `err` with a footnote; that
is not OOM.
Greyhound retains one polynomial and treats a deterministic prover failure as
a failed observation rather than retrying an identical proof. Its reusable key setup remains
embedded in commit, so separate setup time is unknown; the expanded key size is
reported from `comkey_len`.

Akita uses uniform full-field coefficients and uniform extension-field points
with the generated `fp32-dense` planner schedule for the requested size. Its
catalog-selected profile is verifier context; the PCS commitment payload is
exactly 128 bytes.
The catalogs shipped in the pinned Akita revisions have production rows at
`nv ∈ {20, 26, 28, 30}`. This harness adds `nv=22` and `nv=24` by running that
same revision's planner (`scripts/extend-akita-fp32-dense.sh`) and installing
the resulting tables from `vendor/akita-catalogs/`. Nearby sizes are never
substituted. Setup-offload rows use a separate recursive catalog generated by
`scripts/extend-akita-fp32-dense-offload.sh`.

## Machine requirements

- **Akita:** Rust 1.95, any host that can build the crate graph.
- **Greyhound:** Linux x86_64 with AVX-512F for headline numbers (`BACKEND=auto`
  uses the upstream AVX-512 NTT). The reference also has a portable backend;
  do not mix that ISA into this table. Apple Silicon cannot produce headline
  Greyhound rows.
- **RoKoKo:** `rustup` `nightly-2026-09-03`. The pinned revision has one
  ring-arithmetic backend (`incomplete-rexl`, with AVX-512 and IFMA kernels and
  a portable fallback). Headline numbers should still be gathered on the same
  AVX-512 Linux box as Greyhound. The worker builds upstream's default features
  and default ring spec (`rings/default.toml`) once and selects the parameter
  set with the executor's command-line argument (`rokoko p-26`), as upstream's
  own benchmark script does. Set `MIMALLOC_PURGE_DELAY=-1` (the wrapper does this).
  `fetch-vendors.sh` patches the pinned executor so it prints the inner
  commitment size, expanded CRS resident size, and `/proc/self/status` peak
  RSS; the independent full-witness claim check remains enabled but lies
  outside the prover timer.

Do not mix machines, ISAs, or thread counts when filling the table.

## Commands

The generated `report.md` / `report.tex` include this sequence. Runs default to
one warmup and ten measured samples with recorded workload seeds.

```bash
source "$HOME/.cargo/env"   # if cargo is not on PATH
rustup toolchain install nightly-2026-09-03 -c rustc,cargo   # once, for RoKoKo
export CARGO_NET_GIT_FETCH_WITH_CLI=true
export RUSTFLAGS="-C target-cpu=native"
export RAYON_NUM_THREADS=1

./scripts/fetch-vendors.sh          # Greyhound, RoKoKo, and Akita pins
./scripts/extend-akita-fp32-dense-offload.sh third_party/akita   # once; fills the offload catalog
./scripts/build-greyhound.sh        # AVX-512 host only; -march=native

# Planned matrix (no execution): native parameters and any unsupported cells
cargo run -p pcs-bench-runner --bin pcs-bench -- lattice-eval matrix

# One scheme, one payload, one measured sample (must verify, status ok)
./scripts/lattice-eval.sh run --scheme akita --payload 31 --runs 1 --warmups 0
./scripts/lattice-eval.sh run --scheme akita-offload --payload 31 --runs 1 --warmups 0

# New measurements default to 1 warmup + 10 measured processes and varied,
# recorded workload seeds. Use --seed-mode fixed in a separate machine-noise run.
./scripts/lattice-eval.sh run --out results/lattice-x86_64

# Rebuild Markdown + LaTeX from the JSONL in that directory
cargo run -p pcs-bench-runner --bin pcs-bench -- lattice-eval compare \
  results/lattice-x86_64 --out-dir results/lattice-x86_64
```

Each run writes `records.jsonl`, `table.md`, `table.tex`, `report.md`,
`report.tex`, and `provenance.txt`. The report includes the host CPU, AVX-512
status, recorded commit hyperlinks, both paper tables, medians and conservative
distribution-free 95% confidence intervals when supported, and the commands
above.

Warmup processes are stored with `warmup: true` and are excluded from the
median.

## Security targets and accounting

Generated Markdown and LaTeX reports include the following security accounting:

| Scheme | Security bits | Scope |
| --- | --- | --- |
| Akita (direct and offload) | 128-bit target | Planner-validated Module-SIS and classical-ROM transcript targets |
| Greyhound | 128-bit SIS target | Euclidean SIS under ADPS16 quantum core-SVP, using `l2-quantum128-adps16`; not a validated end-to-end transcript bound |
| RoKoKo | < 100 bits | Fixed native profiles on the default ring; heuristic soundness accounting |

These scopes are not equivalent security guarantees. RoKoKo's `< 100 bits`
label is a reporting category, not a precise validated estimate. The detailed
[security analysis](rokoko-security/README.md) records the component calculations
and remaining assumptions.

Sources: Akita's pinned planner catalogs; the Greyhound policy in
`crates/pcs-bench-core/src/lattice.rs` and the worker configuration; RoKoKo's
`rings/default.toml`, `src/common/short_challenge.rs`, and
`src/instantiation.rs` at the pinned revision listed above.

The pinned RoKoKo revision keeps \(q = 2^{50}-2687\), ring degree 128,
challenge weight 22, two fine-projection batches, and the same top-level
`p-22` to `p-30` chains as the previous pin `26d07c73`. Upstream changed three
things in between:

- the challenge operator-norm bound is 9.8 instead of 10.0;
- in the first recursion level, the coarse-projection decomposition base is
  \(2^8\) instead of \(2^9\) for `p-22` to `p-28`, and the opening and
  coarse-projection commitment ranks are 4 instead of 2 for `p-30`;
- the parameter sets are a run-time argument instead of Cargo features.

Upstream's commit subjects for the first two say they bring its last-layer and
second-layer commitment estimates to 128 bits. Upstream also ships opt-in ring
specs with degree-4 slots, a \(2^{128}\) fold-challenge space, and three
projection batches (`rings/n128_d4.toml`, `rings/n256_d4.toml`). They are not
the default, upstream's benchmark script does not select them, and this harness
does not measure them. The `< 100 bits` category describes the default ring.

### Akita schedule provenance

The current Akita pin is used without modifications. The worker embeds its
upstream direct/offload `.aks` artifacts plus supplemental direct rows generated
by that same unmodified planner and committed under
`vendor/akita-catalogs/5d765c9a/`. See `scripts/generate-akita-direct-artifacts.sh`
for regeneration. Artifact decoding and validation are included in setup time.
Updating the pin requires rerunning both Akita lattice rows as well as the six
Akita hash-comparison variants; historical observations keep their original
implementation revision until replaced.
